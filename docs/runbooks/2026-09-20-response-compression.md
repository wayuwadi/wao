# 文档列表回源压缩修复

线上客户端在 2026-09-20 有文档列表 60 秒超时，成功请求也有约 51 秒耗时。
在 Linux2 使用同版本 `2e4b61c` 镜像，以 `local-cloud` 配置和只读 JDBC 连接复用真实
数据库，关闭后台任务及迁移，仅绑定共享网络命名空间的 loopback 18080，不发布端口。

对同一份 678 篇文档读取结果做单次 A/B：

- 未压缩：52,612,638 字节，处理和 loopback 传输 0.70 秒。
- gzip：13,300,066 字节，处理和 loopback 传输 1.13 秒。
- 解压后 JSON 的 `data` 逐项完全相同，不修改正文、反链、版本或任何文档契约。
- 同环境任务列表为 1,503,574 字节，0.14 秒。

这证明文档接口具有较大传输负担，不能把浏览器总耗时全部归因于 SQL。
云端 Nginx 已开启 gzip，但只能减少云端到浏览器的流量，不能减少此前的家庭节点回源量。

生产 Spring Boot 应用对协商 gzip 的 JSON、纯文本与 Markdown 响应启用 2 KiB 起压缩。
不增加超时、不缓存私有数据、不改变列表内容，也不把 SSE 或二进制响应纳入压缩类型。
验证必须包含穿过 Gateway 的 `Content-Encoding` 和解压后内容一致性；loopback 数据
不能被表述为真实浏览器延迟。诊断容器测量后删除。

现有全量文档契约仍返回完整正文。若数据继续增长，后续需按契约迁移到摘要列表和详情按需
加载；本次故障恢复不擅自删减字段，以免影响编辑与草稿恢复。
