# 整体导航与个人布局整改

## 用户结果与硬约束

找功能与切换功能优先。保留现有左侧、顶部、底部停靠、右侧工作区 Tab 和直接拖拽、右键、排序、改名、显隐、打开方式。标准功能归属与个人显示位置分离；已有布局不能被推荐布局覆盖。

## 数据契约

新增 `/api/navigation/layout` GET / PUT，服务端从登录会话确定成员，不接收成员 ID。数据仍使用现有 member_preference 表，独立保留键 `navigation-layout-v1`；通用偏好写接口禁止覆盖此键。JSON 包含 schemaVersion、成员菜单布局与分组、可选锁定标记。只保存导航展示字段，不接受应用地址、权限、健康接口等系统配置。

返回 `{ revision, layout }`；不存在时 revision 为 `none`、layout 为 null。PUT 提交 expectedRevision 与布局，使用 insertIfAbsent / compareAndSet 原子更新；冲突返回 409。布局损坏时明确报错，不把损坏当作空布局。字节和条目数量限制须匹配 MySQL TEXT 容量。

全局内置和应用注册表保留为能力与默认布局来源。个人首次保存原样快照当前有效布局，后续新注册能力默认不常驻；被全局删除的外部应用不能由个人快照恢复为有效应用。旧群组名称、位置和显示名全部保留，可选择推荐分类预设。用户字段版本独立于全局注册表版本。

## 发布

作为一个整体导航需求交付一个 PR。按 AGENTS 与批量发布技能跟进合并、上线和真实链路验收。设计文档中的 30% 耗时改善和 90% 成功率是用户试用目标，不以自动化测试冒充已达成。未验证项逐项记录，不用整体“完成”掩盖剩余工作。

## 刷新与切换时的设置草稿

菜单及快捷链接未保存输入按当前成员保存在本机。刷新或返回设置后恢复，仍需明确保存才改变账号布局；保留原编辑版本以继续执行冲突保护。保存成功清理草稿；本机存储不可用时保留离开确认与刷新保护。成员变化时重新挂载设置表单。
