# Phase 1：AI Run 批量部署与交付阶段

对应任务：`t1787823484656`（关于 AI 任务后的部署和流程的优化）。决策见
[ADR-144](../adr/144-batched-ai-run-delivery.md)。

## 用户结果

- 多个 AI Run 在相近时间完成代码时，main push 先进入五分钟批处理窗口，同一批只执行一次 Jenkins 构建和三节点发布；
  成功批次保持静默，失败批次最多通知一次。运行中的发布不被新 push 中断，后续 push 合并到唯一待执行批次。
- 首页运行卡片和任务内 AI 档案明确展示“编写代码 / 代码完成”“等待部署”“部署成功或失败”，不再让用户从一串
  Jenkins 轮询文本猜任务卡在哪一步。
- 一个旧 Jenkins 构建失败不会把仍等待后继批次的所有任务判失败。后继成功构建只要包含某任务的合并提交，该任务就可以
  继续线上验收并进入待验证。

## 工程约束

- 批次变更范围从线上实际前端版本到构建头计算，覆盖批次内所有需求；线上版本不可确认才依次使用 Jenkins 上一次成功
  构建、上一次构建作为保守回退。
- GitHub `jenkins/wao-main-cd` 状态写到批次内每个提交，目标链接统一指向承担该批次的 Jenkins 构建。
- 批次提交清单必须保留到成功或失败状态回写和飞书通知结束，再由 Declarative Pipeline 的 `cleanup` 条件清理；
  不得在更早执行的 `always` 条件中删除，否则批次头之外的提交会永久停留在 pending。
- AI 在合并 PR 后通过 Runner 结构化进展切换到 waiting_deployment；最终 SUCCESS 仍必须同时具备相关部署成功、线上
  用户链路和通知策略证据，不能把“代码已完成”冒充“任务已完成”。
- 任务业务状态保持现有语义：等待部署时仍是“AI 进行中”，部署和线上验收通过后才由成功运行推进到“待验证”。
- 滚动升级期间旧服务端或旧运行没有 deliveryStage 时，前端继续使用既有运行状态，不出现空白或报错。

## 验收标准

- JCasC 中 `wao-main-cd` 的 quiet period 为 300 秒；批次含多个提交时变更规划和 GitHub 状态覆盖全部提交，成功不发飞书
  卡片，失败只发原因和详情入口（见 ADR-152）。
- 上一批部署失败后，新批次成功会把仍未上线的祖先提交状态更新为 success，线上前端版本等于新批次头的七位 SHA。
- Runner 只接受 AI message 中独占一行的等待部署标记；命令内容、任务 Markdown 和工具参数中的相同文本不会改变阶段。
- 运行卡片在 waiting_deployment 显示“代码已完成 · 等待部署”，档案显示三步进度；部署成功、部署失败和代码失败文案互不混淆。
- 后端测试、Runner 测试、前端单测、类型检查和生产构建通过；main Jenkins 终态成功，线上真实账号可看到新阶段，成功
  构建没有飞书卡片。
