# Phase 1：统一账号与登录体系

## 目标

一个 WAO 账号可绑定邮箱密码、飞书和微信多个登录身份，所有方式进入后得到同一个 `memberId` 和同一套业务数据。登录态由服务端共享会话确认，禁止以前端本地字段冒充用户。

## 验收场景

1. 邮箱注册或登录成功后设置 30 天持久的 HttpOnly 会话 Cookie；刷新、切换标签页、关闭并重新打开手机
   浏览器或 H5 主屏幕应用仍保持登录，30 天未活动或显式退出后立即失效。
2. 娃哥与娃弟在不同设备登录时，`GET /api/auth/session` 返回各自成员，前端不再回退为固定的“娃哥”。
3. 飞书授权成功后，以外部稳定标识查找 `account_identity`；首次登录只能绑定一个尚未认领的成员。需要新增成员时先走邮箱注册，避免第三方昵称静默生成重复成员。
4. 登录页默认只突出飞书扫码，邮箱作为弱化切换入口。当前个人认证主体不具备微信网站登录权限，登录页隐藏微信入口；后端与账号绑定能力保留，取得权限后再恢复入口。飞书二维码 SDK 创建 iframe 前必须移除加载占位，按容器宽度等比缩放 300px 内容且不得出现滚动条；扫码成功后由原浏览器完成 OAuth 回调，授权登录始终以明确的次级按钮呈现。
5. 邮箱、飞书和微信绑定到同一 `account` 后，无论使用哪种方式登录都返回相同 `accountId` / `memberId`。
6. 密码使用 BCrypt；连续五次失败锁定十五分钟；响应不泄露邮箱是否存在或密码是否正确。
7. 未登录访问受保护 `/api/**` 返回 HTTP 401；`/api/hello`、`/api/auth/**`、`/api/share/**` 和公开图片内容不受影响。
8. Google 与企业 SSO 演示入口删除。未取得实际登录权限的第三方方式不得在登录页展示，不伪装成可用。
9. 飞书四种场景均可用：登录页内嵌二维码、登录页授权按钮、工作台端内免登、工作台 PC 端唤起浏览器免登。
10. 组织与成员页必须读取 `/api/org`、`/api/members` 的数据库数据，成员数量实时计算；不得从 `fixtures.ts` 构造账号。成员名称和头像文字可通过 `/api/account/profile` 持久化修改。
11. 生产部署必须把私有环境文件显式传给 Docker Compose，不能只依赖执行用户的 Shell 环境；发布验证应多次命中公开飞书授权入口，覆盖负载均衡后的所有应用节点。
12. 管理员可从“系统设置 → 系统登录配置”维护微信公众号登录开关、App ID、App Secret 与回调 Token；两个
    密钥只回脱敏状态，保存后所有节点立即使用数据库配置，未迁移时兼容部署环境变量回退。

## 暂不包含

- 短信验证码登录：需要短信供应商、实名模板和成本控制，当前以邮箱密码作为可恢复的本地登录方式。
- 自动合并两个已经各自产生业务数据的账号：身份冲突时拒绝绑定，等待独立的可审计合并功能。
- 邮件验证码及找回密码：需要邮件发送服务配置，正式版本前必须补齐后再关闭开发期开放注册。
