# ADR-051：按出站依赖划分 AI 写路由并主动摘流应用节点

## 状态

已采纳。补充 ADR-050 的滚动发布顺序，并进一步收窄 ADR-034 对 `/api/ai/**` 的全量单节点路由。

## 背景

云 Nginx 曾把全部 `/api/ai/**` 固定到 Linux 主节点，理由是 AI 入队或 Runner 领取时可能刷新
Codex 令牌。但现在的自主目标创建、运行入队、状态轮询、Runner 心跳与结果回传只访问共享数据库；
只有账号管理、集中凭据下发和领取携带账号的运行才可能访问供应商。把前一类接口也固定到 Linux，
会让主节点发布重启、DDNS 地址过期或 Gateway 短暂不可用直接表现为用户点击“让 AI 开始”返回 502。

ADR-050 已把主、从节点改为先后发布，并为纯读请求增加容错；但 Nginx 仍可能把非幂等 POST 分给
正在重启的节点，而且把 AI 写请求整体固定到 Linux，截图中的目标创建在主节点发布时仍会失败。

## 决策

- AI 专用 upstream 只承载会发生服务端供应商出站或明文凭据下发的接口：
  `/api/settings/ai-accounts/**`、`/api/ai/runner/accounts`、`/api/ai/runner/claim` 和
  `/api/ai/runner/assistant/claim`。这些接口继续固定到具备 VPN 出口的 Linux 主节点，不回退 Windows。
- `/api/ai/goals`、`/api/ai/runs`、Runner 心跳、控制、进度和结果回传等编排接口走普通双节点 upstream。
  入队时只校验账号存在、启用状态和 provider，不读取凭据；令牌续期延后到 Runner 领取阶段。
- 天人解读的 SSE 长请求按 ADR-047 保持 Linux 专用 upstream 与 330 秒超时，本 ADR 不改变该边界。
- CD 保持 ADR-050 的 Windows 从节点→云前端/Nginx→Linux 主节点顺序。正式发布前先把摘流脚本和模板
  安装到云端；发布一个当前健康的应用节点前，Nginx 把它标记为 `down` 并重载，节点健康后再恢复。
- 摘流期间用 `/run/wao-nginx-upstreams/deployment.lock` 暂停每分钟 DDNS 自动渲染，避免定时任务覆盖临时
  upstream 状态；无论发布成功或失败，流水线退出前都尝试恢复两个节点。
- 只有从节点在云端健康探测通过时才摘流主节点。从节点离线时不主动移除唯一可用的主节点；此时主节点
  自身重启仍可能产生短暂单节点中断，这是当前拓扑在没有第三应用实例时的明确限制。

## 后果

- 用户创建 AI 目标、查看运行状态和 Runner 上报不再依赖单台 Linux 主节点，双节点部署时可跨发布窗口工作。
- Codex 设备码、令牌刷新、额度查询和集中凭据仍只从 Linux VPN 出口发起，不扩大凭据或区域风险。
- 发布耗时只增加摘流与 Nginx 重载时间；正常双节点状态下，新请求不会进入正在替换的节点。
- Windows 从节点离线时仍按原策略自动跳过，无需人工介入；下一次主分支发布会继续尝试补齐。
