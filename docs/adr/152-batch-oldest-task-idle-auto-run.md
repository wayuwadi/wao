# ADR-152：空闲后按项目并发批量推进最早待办

## 状态

已采纳。

## 背景

ADR-114 的空闲调度每个五分钟检查窗口只选择一条任务。即使所选项目和 Runner 已配置多个并发槽位，首次触发也
只会占用一个槽位，其余明确可做的待办至少要等当前运行全部结束、重新累计空闲时间后才有机会进入队列。这与“记录
点子后尽快看到一批真实初版”的使用方式不一致。

## 决策

- 自动推进设置增加“单次推进数”，范围 1 到 10。升级时按策略所选项目当前的 `max_parallel_runs` 回填，缺少
  可用项目配置时回落为 2；以后保存时不得超过所选项目的当前并发上限。
- 一次到期检查按 `created_at / id` 的既有稳定顺序选择最早 N 条匹配任务，并通过现有批量入队接口为每条任务创建
  独立 AI Run，全部固化 Plan 模式。任务不合并上下文、分支或 PR，仍遵守一个任务一个交付链路。
- 项目并发配置后来调低且旧策略值尚未重新保存时，调度和页面总览都立即采用两者较小值，不因存量配置失效而整批
  失败。Runner 的在线槽位继续决定这些已入队运行何时真正领取，暂时没有槽位的运行保持排队。
- 数据库五分钟窗口仍只抢占一次；同批候选由 AI Run 的活动运行去重继续防止与人工派工竞态。每个真实创建的运行
  继续发送一张闲置触发通知，个别通知失败不回滚已经入队的其它任务，最近检查结果汇总本批运行数与通知失败数。
- ADR-114 的空闲计时、项目和状态范围、断网窗口、草稿防覆盖及失败重试语义保持不变；本决策只取代其中“每次只
  推进最早一条”的限制。

## 后果

- 空闲触发可以一次填满所选项目允许的并发槽位，多个点子更快进入独立实现和真实交付链路。
- 调大单次推进数会更快消耗真实 Token，并可能在 Runner 忙碌时形成排队；页面明确展示项目并发上限和排队语义，
  用户可以随时把该值调低。
