# ADR-025：AI Run 以部署成功为完成标准，失败可基于报错重跑

## 状态

已采纳。

## 上下文

AI Run 之前把「AI CLI 进程结束且回了 SUCCESS」当作完成：任务随即进入「待验证」，用户收到结果。但代码合进 `main` 只是流程的一半，`main` 的 push 才触发真正的部署；部署挂掉时用户拿到的是一个「成功」的结果摘要，线上却还是旧版本。PR #50 就是这样：Codex 报了成功，CD 因为 Flyway 版本号撞车导致容器起不来，三个节点全部回滚。

失败之后也没有承接手段。唯一能做的是重新 AI run 一次，新的运行完全不知道上一次错在哪，只能从零把同一段路再走一遍——很可能再踩同一个坑。

## 决策

- **完成标准前移到部署。** Runner 交给 AI 的提示词明确要求：合并后必须用 `gh run watch` / `gh run view --log-failed` 盯住 `main` 上的这次部署，直到跑完；部署失败就读报错、修好、重新提交合并，直到部署成功。只有部署确实成功且线上验证通过才可以回 `WAO_RUN_STATUS: SUCCESS`；部署还没结束或最后一次部署是失败的，一律回 `BLOCKED` 并把完整报错写进摘要。
- **失败可以基于报错重跑。** 新增 `POST /api/ai/runs/{runId}/rerun`：对一次已结束的失败运行，创建一条新的运行记录（新分支、新执行档案），用 `ai_task_run.retry_of_run_id` 指回被修复的那一次。
- **报错随任务一起下发。** Runner 领取任务时，`AiRunnerClaimDto.previousFailure` 带上原运行的 `result_summary`；Runner 把它拼进提示词，并明确告诉 AI「相关提交可能已经合进 main，从这个报错继续往下修，不要推倒重来」。
- 重跑受同样的护栏约束：运行还没结束不能重跑，同一任务已有活动运行时不重复入队，项目未启用 AI Run 或没有电脑接入对应工具时直接拒绝。

## 后果

- 「AI 跑完了」和「线上更新了」不再是两件事，用户拿到 SUCCESS 时线上就是新版本。
- 代价是单次运行时间变长：AI 要多等一轮 CD（当前约 3–5 分钟），部署失败时还会在同一次运行里多跑几轮修复。
- 失败链路可追：从任意一次重跑能顺着 `retryOfRunId` 回溯到最初那次失败，页面上串成一条修复链。
- Runner 依赖 `gh` 可用。没有 GitHub CLI 或没有 CD 的项目，AI 会在摘要里说明无法验证部署，按 BLOCKED 处理，不会假报成功。
