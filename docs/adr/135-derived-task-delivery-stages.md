# ADR-135：从任务状态派生交付阶段

- 状态：Accepted
- 日期：2026-08-27

## 背景

任务状态已经区分收集、执行、待验证和人工完成，但用户从产品需求角度回看时仍需自己判断“聊天设想、等待开发、等待验收、已经验证”。如果再给任务增加一份可编辑成熟度字段，同一任务可能同时出现“待验证 + 已验证”等矛盾组合，历史任务也需要迁移和持续校正。

同时，任务详情已经有写入 `task.detail_json` 的自定义属性和完整保存恢复链路。为关键闭环另建一张验收表会重复草稿、保存和权限能力，而把示例结果预填进去又会把模板误认成真实证据。

## 决策

1. 交付阶段只从任务状态确定性派生：`收集中` 是方向探索；`待办 / 进行中 / AI 进行中` 是待开发；`待验证` 是待验收；`已完成` 是已验证。
2. 项目任务页提供四阶段筛选和真实计数，筛选保存在 URL；所有视图使用同一映射，看板同时收窄到阶段覆盖的原始状态列。
3. 阶段筛选不改变任务、不自动推进状态；AI Run 成功仍进入待验证，只有成员人工完成才进入已验证。
4. 任务验收字段复用现有自定义属性，一键只补齐缺失的成功条件、验收证据、端到端耗时、异常与恢复、通知结果，值保持空白等待真实填写。
5. 任务已有“等待”字段继续记录阻塞点；不新增重复的阻塞或日报状态模型。

## 后果

- 全部历史任务立即获得一致的交付分类，不需要 migration，也不存在两份状态漂移。
- 用户可以先从待验收筛选集中处理真实结果，再在任务详情记录成功条件、证据、耗时、异常恢复和通知回执。
- 交付阶段是当前状态的解释，不是跨多轮历史档案；需要审计每次状态变化时继续读取既有任务活动和 AI Run 时间线。
