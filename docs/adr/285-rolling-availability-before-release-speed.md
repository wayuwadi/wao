# ADR-285：完整发布优先保障双节点入口可用

- 状态：已采纳
- 日期：2026-09-27
- 调整：ADR-280 的双节点同时替换与允许公共入口短暂不可用的决定
- 保留：ADR-280 的并行构建、不可变静态制品预传和数据库就绪判定

## 背景

Jenkins #554～#557 在 Linux2 经 MySQL 主库通道获取连接超时后失败。Linux1 的数据库就绪接口仍可响应，但两台节点同时替换、完成后才恢复路由的流程无法保证公网请求持续落到健康节点。维护者要求一台机器故障时另一台继续服务；机器故障与代码故障应区别处理。

## 决策

- 常规完整发布先从云端验证两台 Gateway 的数据库就绪状态，并立即按该状态修正 Nginx 路由。没有健康节点时停止发布。
- 每次仅摘流并替换一台应用。两台原本健康时先 Linux1 后 Linux2；Linux2 原本不健康时先修复 Linux2，Linux1 保持服务。每步都须经过云端直接就绪检查并回流，再检查公共入口，才能重启另一台。云端静态制品预传仍可并行，网页入口在双节点都就绪后才切换。
- Linux1 的 SSH/Docker 预检失败属于可明确识别的机器管理通道故障，仍按 Gateway 实际就绪状态决定是否承载流量；可在它仍健康时继续更新 Linux2，但未更新的 Linux1 不计为完整发布成功。若 Linux1 Gateway 也不健康，不重启唯一健康的 Linux2。
- 任一节点安装或数据库就绪失败，原因可能是代码、迁移、配置或机器故障，不能只靠超时字样自动归类。立即停止后续节点替换，故障节点保持摘流，旧网页保留，构建失败并保留日志供诊断。若确认为机器问题，修复后重新发布同一目标版本。
- Nginx 配置测试或 reload 失败时，恢复原配置和摘流标记；流水线退出时若无法恢复预期路由，明确输出告警，不静默吞掉错误。

## 边界

- Jenkins 控制器只运行在 Linux2；Linux2 整机不可用时本流水线无法在 Linux1 上继续执行。要实现控制器容灾，需要独立迁移或增设备用控制器。
- MySQL 写主位于 Linux1，两个应用节点都依赖它。Linux1 整机或写库不可用时，双应用节点不等于业务可用；需单独设计数据库故障切换。
- 只有一个健康应用节点时不能在保持 API 连续可用的同时原地重启它；单节点零中断发布需要蓝绿实例或额外容量。
- Linux2 专用 VPN 出口、媒体本地卷等功能无法由 Linux1 完整接管，见 ADR-277。
