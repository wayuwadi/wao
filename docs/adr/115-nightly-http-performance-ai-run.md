# ADR-115：HTTP 性能夜间巡检进入真实 AI Run

## 状态

已采纳。

## 背景

浏览器端 HTTP 监控已经能保存成员的真实端到端耗时，但治理仍依赖成员打开页面、查看最慢接口并手工派工。
2026-08-25 的最近 24 小时快照显示 3968 次请求平均耗时 1413ms、P95 为 10005ms；其中
`GET /api/tasks` 平均 5894ms，675 次中 637 次达到慢请求阈值。只修复这次暴露的问题不能防止数据量增长后
出现新的瓶颈，因此需要每天留下可执行的巡检闭环。

## 决策

- 复用自动化域的真实 `JobHandler` 和 Cron 领取协议，内置「HTTP 请求性能夜间 AI 巡检」，每天上海时间
  01:30 触发；不另建节点本地定时器，双节点继续通过 `next_fire_at` 条件更新只执行一次。
- 处理器精确选择已启用 AI 工作流的「Wa All in One」项目，以项目负责人作为任务创建人和指标归属成员。
  读取最近 24 小时真实 HTTP 指标，把窗口汇总与最慢接口聚合写入任务目标，再调用既有自主目标入口原子创建
  Task 与 AI Run。Runner、仓库、分支、PR、部署和飞书结果继续遵守既有 AI Run 约束。
- 指标窗口为空时只在自动化历史中记录跳过，不创建无证据任务；项目工作流、公网分享地址或 Runner 能力不可用时
  真实执行器失败，并由自动化历史保留有界原因。AI 收到的任务明确要求核对仓库根因、保持行为与权限、执行测试并
  用下一窗口实测复验；不得用模拟数据或未经测量的提速比例宣称成功。
- 当前成员隔离不被巡检绕过：任务只携带项目负责人的聚合指标，不包含最近请求明细、查询参数、正文、Cookie 或凭据。

## 后果

- 性能治理从人工偶发检查变成每日真实数据驱动的开发派工；每次有指标的检查会消耗一次项目 AI Runner 槽位与额度。
- 项目负责人之外成员的私有指标不会进入巡检任务，因此该任务反映项目负责人的实际网络体验而不是伪装成全站监控。
- 工作流暂不可用时不会留下永远排队的半成品 Task；修复条件后可以从自动化页面手动运行或等待下一次 Cron。
