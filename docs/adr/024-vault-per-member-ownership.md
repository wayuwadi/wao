# ADR-024：密码库按成员归属

## 状态

已采纳。

## 上下文

`vault_group` / `vault_item` 建表时没有任何归属信息，`GET /api/vault` 返回全库分组，增删改查也只按 id 定位。结果是任何登录用户都能看到、打开甚至解密别人创建的密码库条目——包括 `POST /api/vault/items/{id}/reveal` 返回的密码明文。

密码库是全站敏感度最高的数据，服务端静态加密（ADR-009）只解决了「落库不是明文」，没有解决「谁能读到」。

存量数据无法还原创建人：库里既没有 `created_by`，也没有任何间接线索。

## 决策

- `vault_group` 新增 `owner_member_id`，归属由服务端从当前会话推导（`CurrentMember`），不接受请求体指定。
- 条目的归属跟随所在分组，不单独记一列：一个条目要么在自己的分组里，要么就不该被看见。
- 所有 `/api/vault/*` 接口都在「当前成员自己的分组」范围内工作。访问别人的分组或条目一律按 `404 不存在` 处理，而不是 `403 无权访问`——后者等于确认了这个 id 真实存在。
- 「未分组」从全局唯一的 `vg-default` 改为每人一个（`vg-default-<memberId>`），按名称识别，不允许删除。前端也改为按名称判断默认分组，不再硬编码 `vg-default`。
- 存量分组在 V23 migration 里统一归到组织管理员 `wg`（娃哥）。这是没有创建人信息时唯一可执行的选择；数据本身不删除，需要移交时改这一列即可。

## 后果

- 每个人只看得到自己的密码库；共享密码需要各自保存一份，本阶段不提供分享机制。
- 迁移后其他成员的密码库会「消失」在自己的视图里（数据仍在 `vault_group` / `vault_item` 中，只是归属在 `wg` 名下），需要管理员按需改 `owner_member_id` 移交。
- 关掉登录保护的本地 / dev 环境只有一个身份，按 `wg` 处理，与存量归属一致，不影响演示。
