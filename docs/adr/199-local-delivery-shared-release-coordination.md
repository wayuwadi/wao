# ADR-199：本地交付与共享发布协调

## 状态

已接受（2026-09-04）。按用户确认的开发部署流程，取代 ADR-144 决策 6 和后果中“每个 AI 运行必须等待部署后才结束”的要求；保留一个需求一个 PR、五分钟合批、不可变制品和严格滚动发布。

## 原因

Jenkins 已能合并相邻 main push，但开发线程仍受旧交付规则约束，各自等待和轮询同一流水线。生产发布耗时因此同时占住多个开发线程，并被误当作每个需求独立的交付门禁。

## 决策

- 各开发线程独立完成本地开发、相称测试及真实用户链路验收，按既有授权提交和合并 PR。完成后明确报告本地结果和发布待确认状态，不阻塞其他需求开发。
- 一个 Jenkins 任务只由一个协调者处理发布计划与后续检查。其他线程交付 PR、合并 SHA 和本地证据，不各建一个部署监控。若没有可共享的协调设施或明确负责人，则先交付状态，不伪称已建立跨线程协调。
- 已在运行的构建仅覆盖实际检出的提交。检出后的新合并由唯一待执行批次按启动时最新 main 汇总；不为了某个 PR 额外 Build、取消、重启或缩短静默窗口。
- 用最近 5–10 次可确认的成功生产部署耗时中位数估算，排除失败、中止、未结束和纯文档/测试批次，加上至少两分钟或 20% 的余量。排队时间和当前运行剩余时间按实际并行等待关系计算，不重复相加。
- 到预计检查时间后一次读取状态；没有可执行变化不反复通知。长时间超预期只由协调者检查和报告一次原因，不由所有线程并行重跑。
- 历史不可读时明确说明估时依据不足，使用暂定检查时间或交还用户；不绕过登录、不把估计当完成时间。任务结束后的回访必须依赖已实际创建且去重的调度任务，不用聊天承诺替代。
- 本地交付完成与上线成功分别表达。线上成功仍要求相关 SHA 被成功发布批次覆盖以及线上健康证据；旧批次失败不误判为后继批次内新 PR 的失败。

可执行流程放在项目 Skill `wao-dev-batch-delivery`，可独立分享。此变更调整 AI 协作规则，不修改 Jenkins 构建配置或 WAO Runner 的既有状态机。

## 验收

验证并行 PR 共用一个排队批次、已检出后新提交进入下一批、历史不足、超时与失败后有后继批次等情形。文档与 Skill 变更本身不要求额外生产发布；若此前仍有未上线运行时代码，既有流水线仍可能将其一起发布。
