# ADR-176：飞书三阶段任务表情与认证轮询派工

## 状态

已采纳（2026-08-31），修正 [ADR-172：可配置飞书任务表情工作流](172-configurable-feishu-task-reaction-workflow.md) 中“已收下同时用于人工派工”以及“只能依赖事件回调”的决策。

## 背景

真实需求是 `GET → StatusInFlight → DONE` 三个含义不同的阶段：机器人保存任务后表示已了解；成员认为内容
可以执行时添加飞机；AI Run 执行期间保持飞机，完成待验收后添加 Done。[ADR-172：可配置飞书任务表情工作流](172-configurable-feishu-task-reaction-workflow.md) 把前两个阶段合并成同一
设置，后端因此只监听默认 `GET`，成员添加飞机不会触发。

生产环境已经配置飞书自建应用 App ID / Secret，消息主动轮询可以正常建任务，但没有配置 Verification Token
或 Encrypt Key。现有代码只在可信事件回调通道调用表情派工服务，因此真实飞机表情没有进入任何派工记录。
飞书开放 API 本身提供经过 tenant_access_token 鉴权的消息表情列表，返回 reaction_id、操作人、时间和表情类型。

## 决策

1. 表情工作流拆成三个独立配置：`receivedEmoji` 默认 `GET`，`triggerEmoji` 默认 `StatusInFlight`，
   `completedEmoji` 默认 `DONE`。旧部署没有新设置键时直接采用安全默认值，不新增 migration。
2. 快速收集成功只添加 received；AI Run 成功入队后添加 trigger；成功进入待验收后添加 completed。
   失败继续添加 `ERROR`，表情失败不反向改变任务运行终态。
3. 人工派工只识别 trigger。无论来自事件回调还是认证轮询，都必须同时满足：原消息已经创建任务、操作人为
   user、操作人绑定到任务创建者、真实 AI Run 门禁通过；`reaction_id` / 事件 id 持久去重。
4. 现有 15 秒新消息轮询与一分钟编辑回看在处理合格消息后读取指定 trigger 表情。已有派工记录的消息不再
   请求表情接口；轮询要求飞书按跨应用稳定的 Union ID 返回操作人，不能用当前机器人应用专属的 Open ID
   去匹配登录应用身份。双节点同时看到同一表情由数据库唯一键收敛为一次运行。
5. `im.message.reaction.created_v1` 事件订阅继续保留为低延迟通道，但不再是人工派工可用的必要条件；
   Verification Token / Encrypt Key 仍是公开回调进入派工链路的必要安全门禁。

## 后果

- 默认交互与用户看到的语义一致，Get 不再意外启动任务，飞机才是明确执行动作。
- 已有自建应用授权即可工作；回调暂未配置、偶发丢失或延迟时，认证轮询仍会在有限窗口内发现表情。
- 飞书不允许机器人删除成员本人添加的飞机，因此完成时新增 Done；机器人自身添加的阶段表情不冒充对成员
  表情的所有权变更。

## 验收

- 单元测试覆盖三个默认/自定义配置、回调飞机、认证轮询飞机、创建者身份、reaction_id 幂等和阶段回执。
- 设置页显示并分别保存 Get、飞机、Done，明确认证轮询可用、事件订阅用于降低延迟。
- 线上在真实快速收集原消息添加飞机后产生一条 Plan AI Run，并在原消息看到执行中与完成待验收回执。
