# ADR-248：任务保存使用账号隔离的持久操作回执

## 问题与行为

原有稳定任务 ID 的 PUT 可以避免生成两个任务 ID，但不能区分“数据库已提交、响应丢失”和“没有提交”。
直接重试旧全文还可能遇到自己上次提交造成的版本冲突；新建弹窗重开后只恢复文本，也可能生成新任务 ID。

新增 `PUT /api/tasks/{taskId}/operations/{operationId}`，请求为 `{accountId, task}`。
accountId 仅用于检测发送期间账号变化，服务端以真实会话账号认证，二者不一致拒绝写入。
MySQL 以账号与 UUID v4 操作 ID 为唯一键，并记录操作类型、任务 ID、规范化 DTO 的 SHA-256 和 gzip 压缩回执。
同键不同任务或内容返回 409；请求和任务修改在同一事务提交，失败时均回滚。并发重试等待同一唯一键，不另建任务。
旧接口保留兼容，只有新操作接口承诺该回执协议。任务编辑版本检查和当前权限检查继续有效。

`GET` 同一路径只查询当前账号的回执：`COMMITTED` 返回原任务回执，`UNCONFIRMED` 表示未观察到已提交记录，不能解释成确定未执行。
读取或重放已提交回执前重新检查当前任务权限；任务被删除或权限撤销不会通过历史回执泄露内容。
新建操作没有编辑版本时，若任务已经存在则拒绝覆盖，要求先确认结果。

## 浏览器恢复

发送前持久化操作 ID 与不可变请求快照，存储失败则不发送。连接中断后先查询；无法查询则展示结果待确认并保留草稿。
刷新或手动重试先查询同一操作，未确认时仅用原键、原快照安全重放；收到回执后才以新操作提交后来输入。
仅推进原请求所基于的编辑版本，不把迟到回执覆盖到新输入。支持 Web Locks 时同账号同任务的跨页签发送串行化。
不支持 Web Locks 的浏览器仍依赖服务端操作唯一键及任务版本冲突保护，不承诺跨页签自动合并。

新建弹窗在发送前保存稳定任务 ID，重新打开继续确认同一任务。
新草稿按账号隔离；旧版无账号标识的草稿不删除、不自动归属，提供明确的手动恢复入口。

## 部署与边界

先应用新增 V158、完成两节点部署，再发布新前端；旧 API 始终保留。
写直连开关仍需独立验收后开启；开启后前端仅把具备操作回执的任务 PUT 直连，其他写入保持主域路径。
读取保持有界回退，普通写请求不加入全局自动重放。

回执与数据库一起备份；当前不自动删除历史操作 ID，避免旧草稿变成全新写入。
单次任务请求与原始回执限制 4MiB，回执压缩存储；需监控表增长，后续清理必须保留能拒绝过期重放的摘要标记。
本协议不解决 MySQL 异步复制未接收事务时的数据丢失，也不保证既有事务外通知的严格一次投递。

验收区分单元测试、真实 MySQL 回执并发、真实浏览器任务保存及线上直连故障；不能互相替代。

## 本次验收

2026-09-21，本地应用连接既有 MySQL，八连接并发专项通过；回执单元测试与迁移检查通过。
前端八组 47 项回归、类型检查和生产构建通过。
真实浏览器创建临时任务并编辑：只对该任务的临时验收代理在后端返回 200 后丢弃一次响应，
记录显示同一操作 ID 随后收到 GET 查询，没有第二次 PUT；页面显示保存成功，重新打开验收版本后正文一致。
该证据证明响应丢失后的结果确认，不代表 MySQL 故障切主或节点直连写入已经验收。
