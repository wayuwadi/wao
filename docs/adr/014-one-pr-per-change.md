# ADR-014：交付单元改为「一个需求 / 一个 BUG 一个 PR」

## 状态

已采纳。修订 [ADR-011](011-development-fast-delivery.md) 的第 2、4 条（默认直推 `main`、PR 可选），其余部分继续有效。

## 上下文

ADR-011 为了拿到快速的真实环境反馈，把默认交付路径定成「本地验证通过后直接 push `main`」，功能分支和 PR 降级为可选的协作工具。这确实压掉了云端重复 CI 的等待，但也带来两个实际问题：

1. **变更失去了可寻址的边界。** 多条需求混在一串直推的提交里，事后想定位「任务模块那次改动到底包含哪些文件」，只能靠翻 `git log` 猜范围；回滚也没有一个干净的单元可以 revert。
2. **每次交付都要问一次。** AI 在没有常设授权的情况下，每完成一块工作都要停下来确认「要不要推」，用户反复回答同一个问题。

用户（wayuwadi，仓库 admin）在 2026-07-25 明确要求：以后一个需求或一个 BUG 就是一个 PR，不必再逐次询问。

## 决策

- **交付单元 = PR，粒度 = 一个需求或一个 BUG。** 多条需求不塞进同一个 PR；一条需求也不拆成多个 PR。
- **AI 不再逐次征求同意**：完成与改动相称的本地验证后，直接建分支、提交、push、开 PR、Squash Merge 并删除源分支。
- **PR 不承担 CI 门禁**。CI/CD 只在 `main` 的 push 上触发（`ci-cd.yml` 的 `on.push.branches: [main]`），所以 PR 页面上没有 checks 是**预期行为，不是失败**——不要因为「等 CI」而卡住。合并前的门禁是本地验证全绿 + `mergeable` 为 `MERGEABLE`。
- **push 前必须核对语义冲突**，这类冲突 git 不会报：两边各自新建了同编号的 ADR、同版本号的 Flyway migration，文件名不同所以合并静默通过，但语义上撞车。核对方式是把本地新增的编号和 `origin/main` 上的对一遍，撞了就重新编号。

## 后果

- 每次交付多一次 push + PR 创建 + merge 的往返，比直推 `main` 慢一点；换来的是每个需求都有独立、可回滚、可讨论的记录。
- `main` 上的历史变成一条条 squash 后的需求级提交，`git log --oneline` 直接就是需求清单。
- 飞书通知的节奏不变：仍然只在合并进 `main` 时响一次。
- 本 ADR 与 ADR-011 一样是**开发测试阶段的临时授权**。第一个正式版本发布前必须撤销「不必逐次询问」和「PR 不承担 CI 门禁」两条，恢复受保护分支、PR CI、CODEOWNERS Review 和发布审批。
