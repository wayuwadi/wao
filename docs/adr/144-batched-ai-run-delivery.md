# ADR-144：AI Run 共享 main 批量部署并分阶段展示

## 状态

已采纳。

## 背景

多个 AI Run 可以并行写代码，但每个 PR 合并后的 GitHub push 会立即排一条 Jenkins 生产流水线。流水线又按
Windows → Linux → 云端严格串行发布，所以后完成的 AI 往往先等旧构建、再等自己的构建。2026-08-27 的真实记录中，
`9a1e815`、`4d4813e`、`9c2d11d`、`5a30a5a` 在九分钟内连续进入 main；Jenkins 队列偶发把相邻 push 合并到
#127 / #128，但只有构建头提交收到状态，夹在批次里的提交长期没有自己的终态。随后 #127 至 #138 的部署故障又让
多个仍在等待后继批次的 AI 会话重复解释同一个旧失败。

旧变更规划固定比较 `HEAD^..HEAD`。当 Jenkins 已经把多次 push 合成一条构建时，这个范围只覆盖批次最后一个提交，
可能漏掉更早提交对应的模块测试。AI Run 自身也只有 running / succeeded / failed，页面无法区分代码尚未完成、代码
已经合并但正在排队，以及部署本身失败。

## 决策

1. `wao-main-cd` 设置 300 秒 quiet period。同参数的 main push 在静默窗口内合为一条队列项；已有发布运行时，
   Jenkins 原有的禁止并发规则继续把后续 push 合并到唯一待执行项，不中断正在执行的 migration 或滚动发布。
2. 每条流水线从线上前端公开版本文件解析当前真实部署 SHA，并以它到本次构建头之间的 first-parent 范围生成变更计划。
   线上版本不可解析时才回退 Jenkins 上一次成功构建提交，再退到上一次构建提交；不能再固定使用 `HEAD^`。
3. pending / success / failure 状态回写到批次范围内每个 main 提交。失败部署不会推进线上版本，因此下一次包含修复的
   成功构建会重新覆盖此前未上线提交的状态；一个后继批次成功即可证明其中所有祖先改动已经随同上线。
4. 批量飞书卡片只发送一次，标题正文展示批次提交数和每个需求级提交摘要；节点发布与最终验收仍沿用严格成功条件。
5. Runner 提示 AI 在 PR 合并后输出结构化的 `WAO_DELIVERY_STAGE: WAITING_DEPLOYMENT`。Runner 只从 AI 文字事件
   识别该标记并上报，不扫描命令或工具参数；服务端把它持久化为 waiting_deployment，前端展示“代码完成 → 等待部署
   → 部署结果”。成功、部署失败和合并前失败分别落为 deployment_succeeded、deployment_failed、code_failed。
6. AI 只采信包含本次合并提交或其后继提交的部署。队列里更旧的构建失败不是当前任务终态，应继续等待后继批次；只有
   最后一个相关批次失败且无法在本次会话修复时才返回 BLOCKED。

## 后果

- 单条孤立提交会多等待最多五分钟，换取并行 AI 任务共享一次构建、制品、三节点发布和飞书通知的机会。
- 批次仍以最新 main SHA 生成不可变制品，严格双节点与线上验收没有放宽；静默窗口不是取消部署，也不允许 AI 在等待
  部署时提前结束运行。
- 线上版本是真实发布基线。纯文档批次可能重复验证尚未部署基线之后的文档提交，但不会触碰生产；任何未上线运行时代码
  都会在下一次构建重新进入计划，避免一次失败后只能靠人判断该重试什么。
- 历史失败无法可靠区分代码和部署阶段，迁移只把历史成功回填为 deployment_succeeded，历史失败统一记为 code_failed，
  不伪造不存在的部署证据。

## 验收

- 配置测试约束 300 秒 quiet period、线上部署基线和批次状态文件；临时 Git 仓库测试覆盖七位线上 SHA解析与回退。
- Runner 测试证明只有 AI 文字标记能切换等待部署，命令事件里的同样文本不会触发。
- 服务测试覆盖等待部署、部署成功、部署失败和合并前失败；前端测试覆盖运行卡片与详情三阶段展示。
- 合并后以 Jenkins 实际批次、批次内提交状态、线上版本和飞书卡片作为最终证据。
