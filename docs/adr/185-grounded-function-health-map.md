# ADR-185：用真实使用与交付提交维护功能健康地图

## 状态

已采纳。

## 背景

工作台能列出功能，但不能回答哪些功能常用、哪些可能难找或重叠。HTTP 巡检只有接口性能数据；若用静态点击率、
通用模板或模型猜测补齐，会把演示结论冒充真实产品事实。人工评分又很难持续，不能作为主要迭代来源。

## 决策

- 登录后的主壳按稳定 `route.meta.module` 记录真实页面打开事件，使用统计按成员隔离；工作台显示当前成员最近 30 天
  打开次数、占比和基于明确阈值的待检查提示。初次上线没有数据时明确显示未知，不回填演示点击率。
- 每个功能默认 1 分。全局分数等于 `1 + 已确认交付提交数 + 人工校准`，并限制在 1 到 100；页面右上角保留
  `+1 / -1` 供人工校准，但不要求成员靠点击维持分数。
- 面向功能的 Conventional Commit 使用稳定功能 id 作为 scope。Runner 只提取本次运行基线后的新提交；运行最终以
  `WAO_RUN_STATUS: SUCCESS` 结束后，服务端才按白名单映射并以 `feature_id + commit_sha` 幂等加分。平台、部署、模糊
  或未知 scope 不猜测功能归属。
- 既有 HTTP 性能 AI 巡检增加功能产品方向，把负责人的真实使用快照、分数和提示放入同一次 AI Run。模型必须核对
  路由、页面和业务边界，再判断入口、路径或重叠问题；样本不足时只报告不足，不生成伪建议。

## 后果

功能地图会从上线后的真实使用逐步形成，不提供虚假的历史基线。一次跨多个功能的变更需要按真实交付单元选择 scope；
单个提交无法可靠表达多个功能时宁可不自动加分，后续由人工校准。使用事件会持续增长，达到需要清理的规模后应新增
保留期或日聚合 migration，不能直接删除现有生产记录。
