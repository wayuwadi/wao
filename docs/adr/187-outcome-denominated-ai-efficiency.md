# ADR-187：AI 效能按有效交付计量并使用同类帕累托比较

## 状态

已采纳。补充 ADR-026、ADR-174 与 ADR-181；不改变 Runner 的 Token 口径、任务验收权限或模型默认值。

## 背景

数据统计页已经能展示真实 Token，并根据模型、思考深度、成功状态和耗时给出建议。但原实现存在三个口径问题：

- 把 `started_at → finished_at` 当作模型速度，实际混入 Git 准备、部署排队和线上验收；ADR-181 后已有
  `ai_execution_duration_ms`，建议却没有使用。
- 跨任务类型按成功率和平均 Token 排出单一“最优”配置，不同难度和交付边界不可比。
- 以运行次数、频率和任务方向描述使用量，无法回答一次部署并线上验收通过的有效结果花了多少。

参考 Uber Engineering 的软件工厂成本拆解，只降低 Token 单价或总量不等于优化；单位消耗必须绑定质量不下降的
业务结果。Uber 的规模和内部基础设施不能直接照搬，本项目先复用已有真实运行、交付阶段、任务验收和用量数据形成
最小闭环。[原文](https://www.uber.com/us/en/blog/efficient-software-factory/)

## 决策

- “有效交付”定义为 AI Run 成功且交付阶段为 `deployment_succeeded`；滚动升级前没有交付阶段的历史成功运行按旧契约兼容。
  合并运行按 `ai_task_run_task` 中每条任务分别计一个结果，同一窗口内重复成功的同一任务只计一次。
- 单位交付 Token = 窗口内全部已结束运行的真实 `total_tokens` ÷ 有效交付任务数。这样失败和重试不会从成本中消失；
  只有全部已结束运行均回传用量时才计算，覆盖不完整时保持未知。已记录的未交付 Token、跨运行重试次数与重试
  Token 单独展示，不把缺失用量补零。
- 质量同时展示已结束运行的交付成功率与有效交付任务中当前已由成员标记“已完成”的数量。AI 线上验收不会代替成员验收。
- 速度比较只使用 Runner 单调时钟回传的 `ai_execution_duration_ms`；端到端时长继续保留观察，但不参与模型路由。
- 模型与思考深度合并为配置，只在同一 `activity_type` 中比较。每个配置至少三次，且每次都具有真实 Token 和 AI 实际时长；
  同类至少两个合格配置才计算质量—Token—时延帕累托前沿。候选仅表示当前样本未被同时支配，不称为全局最优。
- 这些分析由服务端确定性计算，不额外调用模型，不维护供应商单价，也不把缓存 Token 当作等价金额或节省额。

## 后果

- 用户能在数据统计入口直接看到每个有效交付的 Token、真实 AI 时长、验收数量、失败和重试损耗，以及记账覆盖率。
- 样本不足时页面明确给出建立可比评测所缺的条件；不能再用部署较快或偶然成功的一次运行推荐模型。
- `activity_type` 仍是粗粒度任务分类；更细的固定 Eval、工具调用/返回大小和 Runner 内部重试计数需有真实采集后再扩展，
  本次不从日志或提示词估算。
