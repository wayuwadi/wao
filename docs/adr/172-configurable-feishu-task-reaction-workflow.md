# ADR-172：可配置的飞书任务表情工作流

## 状态

已采纳（2026-08-31）。

## 背景

原快速收集链路把 `DONE` 当作“任务已记录”，AI Run 入队后追加飞机，成功后再追加完成勾。真实使用时，
`DONE` 容易被理解成任务已经完成，多个阶段表情并存也不能清楚表达当前要做的动作；成员希望在群聊里确认内容后，
直接添加当前“已收下”表情启动 AI Run，但旧派工逻辑只识别飞机。

人工表情不会出现在已有的 15 秒消息轮询结果中，只能由飞书的 `im.message.reaction.created_v1` 事件送达；
旧设置页把事件订阅描述成低延迟可选入口，未说明这是人工派工的必要条件，造成配置完成的错觉。

## 决策

1. 默认工作流改为 `GET → 保持 → DONE`：任务保存成功添加 `GET`；AI Run 执行期间不追加表情；
   成功并进入待验收阶段后添加 `DONE`。失败仍使用 `ERROR` 并保留既有失败恢复链路。
2. “已收下”表情同时作为人工派工触发器。成员在自己创建任务的原消息上添加该表情后，继续沿用 ADR-155 的
   身份绑定、原消息关系、可信回调、持久幂等、真实项目工作流和 Runner 门禁。
3. 管理员在「自动化 → 飞书群聊同步知识库 → 群聊快速收集」设置“已收下 / 人工派工”和“完成待验收”表情。
   只允许选择 WAO 已经在真实飞书接口中使用过的 `GET`、`DONE`、`StatusInFlight`、`CheckMark`；非法旧值
   回落安全默认值，非法新值拒绝保存。
4. 设置页明确说明人工派工必须订阅 `im.message.reaction.created_v1`，且必须配置 Verification Token 或
   Encrypt Key。消息轮询继续负责收集与编辑同步，不伪装成可以读取表情事件。

## 后果

- 群消息从“已收下”一直保持到 AI 执行结束，阶段含义更稳定；成员不必回 WAO 页面点击启动。
- 已有配置无需 migration；新增系统设置键缺省时直接采用 `GET` / `DONE`，滚动发布期间旧节点仍可读取其他配置。
- 更换“已收下”表情会同步改变新任务回执和人工派工动作，避免页面展示与后端监听值分叉。

## 验收

- 服务测试覆盖默认/自定义表情、非法配置、创建回执、人工派工幂等、运行期间保持与成功待验收回执。
- 前端测试和生产构建覆盖设置加载、保存以及事件订阅必要条件文案。
- 线上由已绑定任务创建者在原消息添加当前触发表情，确认只生成一次 Plan AI Run；运行中不追加阶段表情，
  成功后出现当前待验收表情。
