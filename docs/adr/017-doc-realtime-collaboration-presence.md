# ADR-017：文档实时协同用「共享在场表 + 心跳」，暂不引入 CRDT / WebSocket

## 状态

已采纳。

## 上下文

知识库文档原来右上角挂着两个写死的头像和一个「实时协同」绿点 —— 纯装饰：不管对方在不在线、有没有打开这篇文档，都长那样。真实诉求是三条：

1. 只有当用户**打开了当前页面**，才展示该用户的头像；
2. 像飞书文档一样，支持**同时多人**标记；
3. 有人操作文档中的某一行时，能标出**他具体在改哪一行**。

并且「最终要实时保存，但也要考虑性能」。

约束来自现有架构：

- 部署是双节点（Linux 主 + Windows 从），每个 Gateway 只路由到同机的 `wao-server`（ADR-006），云 Nginx 做节点级故障转移。**两个用户完全可能落在不同节点上**，任何只存在于单机进程内存里的在场状态都会分裂成两半。
- 会话已经是 `spring-session-jdbc`，即跨节点共享状态**走 MySQL** 是这个系统里已经成立的做法。
- 现在没有任何 WebSocket / STOMP 基础设施，Nginx 与 Gateway 也没有为长连接做过配置。

## 决策

**在场（谁在看、在第几行）**

- 新增共享表 `doc_presence`（主键 `<docId>:<memberId>`，字段：光标行、是否在输入、最后心跳时间）。跨节点共享，所以两台机器上的人能互相看见。
- 客户端每 **5 秒**发一次心跳 `POST /api/docs/{id}/presence`，服务端 upsert 自己那一行、返回**在场窗口 20 秒内**其他人的记录。
- 超过 20 秒没有心跳即视为离开。关标签页、断网、进程被杀都能自愈，不依赖客户端一定发出「离开」信号；`DELETE /api/docs/{id}/presence` 只是让头像**立刻**消失的加速手段。
- 页面不可见（后台标签页）时不发心跳，重新可见立刻补一次。

**内容同步**

- `doc` 表加 `rev`，正文或标题变化时自增。心跳请求带上客户端手里的 `rev`，服务端只在**版本落后时**把整篇正文捎回来 —— 一次往返同时干「报到」和「问有没有人改过」两件事，没人改动时应答里只有一个数字。
- 本地编辑仍是 600ms 去抖写透（停手不到一秒就已经在服务端了）。**本地有未写透的编辑时，拉回来的服务端版本直接丢弃**，宁可晚一个心跳周期合上，也不能把用户刚敲的半句话吞掉。

**行级标记**

- `MarkdownEditor` 接一个可选的 `peers`，在正文左侧留一条 26px 的协作轨道：每个人的头像贴在他光标所在的顶层块上，正在输入的那一行再压一道他的颜色条；同一行上多人依次横向错开。
- 自己的光标行由编辑器的 `selectionUpdate` 算出顶层块序号后 `caret-line` 抛出，随下一次心跳上报。
- 只量协作者真正落在的那几行的 DOM 位置 —— 文档几百行时挨个量会明显掉帧，而同时在线的人通常只有个位数。

## 备选方案

- **CRDT（Yjs / Automerge）+ WebSocket**：真正的字符级并发编辑，这是终局形态。但它要引入长连接基础设施、把文档存储从「块 JSON」换成 CRDT 文档、还要处理持久化与快照压缩，工作量与风险都远超本次范围，而当前用户规模是个位数、同时编辑同一篇的情况本就罕见。
- **WebSocket 只做在场广播**：省掉轮询，但仍要为长连接改 Nginx / Gateway，并且跨节点还需要一层广播（Redis pub/sub）。收益只是把 5 秒的延迟降到亚秒级，对「看见谁在这篇文档里」这件事不值这个代价。
- **在场存 Redis**：TTL 天然合适，但 `local` profile 明确不依赖 Redis，而 MySQL 是三个 profile 都有的东西。

## 后果

- 在场变化最长有 5 秒延迟，离开最长 20 秒才消失。对「知道有人在」够用，对「看着对方光标逐字移动」不够 —— 后者要等 CRDT 方案。
- 并发编辑的冲突模型是**每个去抖窗口的最后写入者胜出**（整篇正文覆盖），不是逐字符合并。两个人同时改**同一篇**文档的**不同段落**，后保存的一方会覆盖掉前一方那次窗口内的改动。界面上用「谁在哪一行」把这件事显式化，让人自然避让；真正的并发合并留给 CRDT。
- 每人每篇文档每 5 秒一次写库。个位数用户量下可忽略；如果同时在线人数上到两位数，第一步优化是把在场表换成 Redis 或加写合并，接口契约不用动。
- `doc_presence` 由回收站清理调度器顺带清扫过期行，表不会无限长大。
