# ADR-119：main 发布按变更范围验证并并行构建

## 状态

已采纳。细化 ADR-011 的开发测试期快速交付策略；不改变 ADR-097 的严格双节点成功条件和 ADR-099 的
自建 Jenkins 信任边界。

## 背景

当前每个 `main` 提交都串行执行根 Reactor 全量测试、WAO Web 测试与构建、Agent Web 测试与构建，然后才
开始不可变制品打包和三节点发布。即使提交只涉及一个模块或纯文档，也重复运行所有测试和生产部署。最近一次
成功发布从 GitHub commit status 的 pending 到 success 用时 5 分 48 秒。项目仍在两名用户参与的开发测试期，
更快取得真实环境反馈比对无关模块做重复测试更有价值，但不能用旧制品冒充当前提交或放宽部署失败条件。

## 决策

- Jenkins 在 checkout 后比较部署基线与 `HEAD`，生成后端模块、两个前端、AI Runner 和是否需要生产部署的
  明确计划。Jenkinsfile 只通过显式白名单字段写入未被 Declarative `environment` 预声明的环境变量，不依赖
  管理员批准动态 Groovy 方法，也不会被声明式默认值阻止覆盖。缺少父提交、空 diff、流水线自身变化或出现
  未登记路径时 fail-safe 回退全量验证和发布。部署基线和批次行为由 ADR-144 修订：优先使用线上真实版本，不能再固定为 `HEAD^`。
- 后端使用 Maven `-pl ... -am` 只测试受影响 Reactor 模块；前端只运行受影响应用的 Vitest。后端测试、
  WAO Web、Agent Web 和按需 AI Runner 测试作为并行分支运行。
- 只修改后端 `src/test/**`、WAO Web `src/__tests__/**`、Agent Web 的 `*.spec.*` / `*.test.*` 或 AI Runner
  `test_*.py` 时，只运行对应测试，不生成生产制品，也不触碰生产节点。
- 任何运行时代码变更仍构建两个前端、全部 Java 镜像和 Codex 出口镜像。继续以同一 Git SHA 打包并严格执行
  Windows → Linux → 云端滚动发布和线上探针，不复用线上静态文件，也不给旧镜像补贴新 SHA。
- 纯 `docs/**`、Markdown 和 `.github/**` 变化不产生主站运行制品，因而只执行输入与规划脚本校验；Jenkins
  commit status 和飞书卡片明确标记“验证（无需部署）”，节点状态标记为 skipped，不能伪报生产发布成功。
- 变更分类脚本必须有独立的临时 Git 仓库测试，覆盖纯文档、单后端、双前端、流水线全量回退和无效基线。

## 后果

常见单模块改动减少无关测试等待，三组主要任务的耗时从相加变为取最大值；纯文档提交不再触碰生产。
实际节省量以部署后的 Jenkins status 时间为准，不在落地前承诺固定比例。完整制品构建和严格滚动仍是运行时
变更的主要耗时，这是可追溯 SHA、Windows 离线包和双节点一致性的成本；若以后要进一步缩短，需另行设计
可验证的跨提交制品复用协议。

## 落地校正与验收

- Jenkins #75 证明动态 `env[pair[0]]` 会被 Groovy Sandbox 拒绝；改为六个字段的静态白名单赋值后，#76
  完成全量测试、双节点与云端发布。
- Jenkins #78 证明 Declarative `environment` 中的默认值不会被后续命令式赋值覆盖；移除这些预声明并增加
  `DeploymentRoutingConfigTest` 约束后，#79 再次完成全量发布。
- #76 至 #79 的全量运行显示，约 484 MB Windows 离线镜像包的传输是主要波动来源。继续优化应先设计可校验的
  固定第三方镜像缓存和冷启动恢复协议，不能直接删掉离线依赖包。
