# ADR-155：飞机表情派工与分层通知策略

## 状态

已采纳。

## 背景

飞书快速收集已经能把 `@机器人` 消息持久化成任务，WAO 入队后也会给原消息添加飞机表情，但用户在群里主动添加
同一个飞机表情不会触发任何动作，仍要回到网站点击 AI Run。另一方面，成功交付虽然已默认静默，任务创建、状态变化、
评论等通知仍缺少统一策略，成员也无法决定自己通知中心里的事件范围。

## 决策

1. 订阅 `im.message.reaction.created_v1`，只把用户在 `feishu_quick_collect_event` 已持久化原消息上添加的
   `StatusInFlight` 解释为派工。操作者必须绑定 WAO，且必须是该快速收集消息的原创建者；不按标题或正文猜任务。
2. reaction 事件只在已通过 Verification Token 校验，或确实收到并成功解密 Encrypt Key 信封的可信回调上执行；仅仅
   保存了 Encrypt Key 不会放行明文事件。事件以飞书 `event_id` 持久幂等，无 event id 时使用消息、操作者与动作时间
   摘要。入队和幂等记录同事务提交；双节点或飞书重推不会重复运行，入队失败回滚并给原消息添加 `ERROR`，用户可
   重新添加表情再次派工。
3. 表情派工使用项目默认 AI 工作流、自动执行节点、后台默认模型与推理强度，并固定开启 Codex Plan；项目、Runner 或仓库
   未真实配置时失败关闭，不创建演示运行。
4. 全组织飞书策略存 `system_setting.notification.policy.v1`，只允许管理员修改；默认关闭任务普通动态、任务成功和
   AI Run 成功，保留 AI Run 失败、人工任务通知和无人值守触发说明。项目静音与 Webhook 总开关继续一票否决。
5. 任务详情增加明确的“人工通知到飞书群”动作。普通评论按任务动态策略，含真实 @成员的评论按人工通知策略，避免关闭
   自动噪音后连人工点名也失效。
6. 当前成员站内偏好存 `member_preference.notification-center-policy-v1`，分别过滤任务创建/完成、AI Run 成功/失败和登录；
   未读数与列表使用同一过滤规则，成员之间不读写彼此配置。

## 后果

- 群聊里的原消息同时成为记录、编辑、派工和进度反馈入口；权限与幂等依赖已有真实身份和消息关系。
- 默认通知群只留下失败、人工动作与必要的自动触发说明；管理员仍可按业务需要恢复成功或普通动态。
- 系统策略与个人偏好共用一个设置页面，但后端权限边界独立，普通成员只能编辑自己的站内偏好。

## 验收

- 服务测试覆盖原创建者/他人、重复事件、非飞机表情、Plan 入队、失败回滚与管理员权限。
- 前端测试覆盖设置加载、草稿防丢、权限只读、保存失败重试、人工通知按钮及通知中心紧凑单行。
- 线上以绑定成员在原快速收集消息添加飞机，确认只创建一个 AI Run；成功群卡片保持静默，失败策略仍可用。
