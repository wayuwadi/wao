# ADR-113：多个任务合并为一次 AI Run

## 状态

已采纳。

## 背景

项目任务列表已经允许一次勾选多条任务，但原实现只是一次请求循环创建多条 `ai_task_run`。每条运行仍有独立
分支、worktree 和 AI CLI 会话，用户从飞书机器人或随手记录积累的一组相关点子因此会被拆成多个线程，既浪费
上下文，也要求用户分别跟进。

只在浏览器里把标题拼成一段提示词无法形成可靠闭环：刷新后没有可追溯的任务关系，Runner 重跑和续跑也无法
重新取得同一组真实任务内容，运行完成后更无法把所有原任务统一带到待验证。

## 决策

- 新增 `ai_task_run_task` 关系表，按 `ord` 保存一次运行关联的全部任务；`ai_task_run.task_id` 继续保留第一条任务，
  作为兼容旧接口、通知跳转和历史数据的主任务。V91 为全部历史运行回填一条关系记录。
- `POST /api/ai/runs` 新增 `mergeTasks`。仅合并模式把同一项目的多条主任务创建为一条运行；单任务、子任务和原有
  非合并批量调用保持原行为。关联任务中任一已有主任务活动运行时整体拒绝，不静默漏掉用户选择。
- 合并运行的 `prompt_url` 指向公开只读的 `/api/share/ai-runs/{runId}.md?openOnly=true`。服务端按选择顺序实时读取
  每条任务的标题、描述、图片和未完成且未单独派工的子任务，并在开头明确要求 AI 在一个工作区和一个上下文中
  逐项完成、逐项汇报。任务正文不复制进运行表，后续领取和基于报错重跑仍读取真实任务数据。
- 排队、领取、成功、失败、暂停、掉线回收、续跑和重跑都同步更新全部关联任务；每条任务详情都能回看同一运行。
  首页和飞书仍只产生一条运行记录与一组通知，标题明确展示合并任务数量。

## 结果

用户可以把一组相关任务作为一个交付单元交给 AI，共用一个分支、worktree、会话和部署链路。原任务仍是独立的
验收对象，运行档案和状态不会因浏览器刷新或后续重跑丢失。不同项目不能合并，避免一条运行同时面对不同仓库、
默认分支或 Runner 配置。
