# ADR-097：双节点严格成功与滚动发布

## 状态

已采纳。取代 ADR-092 的 Windows 离线跳过策略，并更新 ADR-050、ADR-051 的发布顺序和成功条件。

## 背景

Windows 重装后，旧 SSH 主机指纹让 Actions 跳过从节点，但流水线仍以 Linux 单节点完成并显示成功。
这无法证明双 Gateway 可用，也无法保证两台机器运行同一提交。目标是日常发布期间始终保留一个应用节点承载请求；
不承诺 Linux 整机断电后的数据库和注册中心故障转移。

## 决策

- Windows 使用独立部署密钥和独立 `known_hosts`。严格验证 SSH、WSL、Docker 和公网 Gateway；禁止关闭主机校验。
- CI 一次构建带 Git SHA 标签的应用镜像，依次部署 Windows、Linux，最后发布云前端。两台机器均通过直连健康、
  从库校验和运行镜像 SHA 检查后才允许整体成功。
- 发布 Windows 时 Linux 保持入流；Windows 恢复入流后才摘流 Linux，并通过公共入口探针证明 Windows 正在接流。
- 任一节点最多自动部署三次。Windows 失败时保留 Linux 当前版本；Linux 失败时保持 Linux 摘流并由 Windows 服务。
  两种情况都将流水线标红，并在飞书分别报告各节点结果。
- 首次从节点重建必须显式使用 `bootstrap_windows`，从主库生成一致性 GTID 快照。正常发布发现复制异常时只失败并摘流，
  不自动清空从库数据。
- 不兼容的新旧 Schema 继续使用显式维护窗口；普通迁移必须满足滚动期间的新旧版本兼容。

## 后果

正常双节点发布可以在应用容器替换期间保持公共 API 可用，绿色流水线明确代表两台应用节点和云入口均已完成。
Windows 长期离线会阻止新版本发布，这是严格一致性的有意取舍；紧急情况下也不提供隐式单节点成功开关。
