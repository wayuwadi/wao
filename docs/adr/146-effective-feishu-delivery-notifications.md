# ADR-146：交付飞书通知只保留行动信息

## 状态

已采纳。

## 背景

AI Run 的派工、领取、开始和结束分别发送卡片，用户在真正需要验收前已经连续收到多条内容相近的消息。
Jenkins 卡片又把完整提交正文和 Windows、Linux、云端、最终验收四组详情全部铺开，单条消息可占满一个聊天屏幕。
通知数量和长度共同掩盖了真正需要处理的结果：成功时不知道具体改了什么、怎么验收；失败时不能快速判断失败范围和原因。

WAO 页面已经持久化队列、领取、执行、等待部署和终态进展，群聊不需要复制这一整条时间线。Git 历史与 Jenkins
控制台也保留完整提交正文和执行日志，飞书卡片可以只承担“告知与引导行动”。

## 决策

1. 普通 AI Run 入队、执行电脑领取和开始执行只更新 WAO 页面，不再发送飞书过程卡片；成功、失败或未报告状态的
   最终结果各发送一张卡片。闲置自动派工、HTTP 性能巡检等需要解释系统为何主动运行的场景，保留一张专用触发卡片。
2. Runner 最终摘要固定使用“改动：/验收：”两段、每段最多三条。AI 成功卡片从真实摘要提取这两段并分别限制为
   220 / 180 字；旧运行缺少结构化段落时明确引导打开任务详情，不推测或补写不存在的改动和验收事实。
3. AI 成功卡片只保留任务、改动、验收和行动按钮；失败或状态不明卡片只保留任务、原因和行动按钮。项目、执行工具、
   执行电脑等可在任务详情查看，不占用群聊首屏。
4. Jenkins 成功卡片只展示批次提交标题清单、提交链接和整体结果；最多展示六条标题，更多改动显示折叠数量。
   完整中文提交正文继续作为 Git 历史证据，但不复制进卡片。
5. Jenkins 失败卡片不展示改动清单，只展示失败范围和原因。失败范围由 Windows、Linux、云端和最终验收的真实状态
   判断为“发布未开始 / 部分完成 / 全部未完成”；原因优先使用失败阶段和部署状态文件中的安全摘要，完整日志通过受保护的
   Jenkins 链接查看。

## 后果

- 普通 AI Run 从入队到结束只产生一张需要人行动的群通知；过程进展仍可在 WAO 实时查看。
- Jenkins 卡片在批次规模增大时仍保持固定短结构，群聊首屏可以容纳更多有效通知。
- 完整原因、逐节点重试详情和提交正文不再直接铺在群里，需要点一次链接查看；这是用通知可读性换取详情按需展开。
- 自动派工触发卡片与最终结果卡片仍可能各一张，因为前者解释无人操作时为何启动，后者要求验收或处理，行动语义不同。

## 验收

- 服务测试证明普通入队和领取不调用通知器，成功卡片只包含任务、“改了什么”和“怎么验收”，失败摘要有限长。
- Shell 测试直接捕获 Jenkins webhook JSON：成功卡片为四个元素且没有完整提交正文；部分部署失败时明确列出节点范围、
  失败阶段和安全原因。
- Runner 测试证明新派工与续跑提示都要求结构化终态摘要，且不改变 SUCCESS / SKIPPED / BLOCKED 判定。
- main 部署后以真实 AI Run 终态通知、Jenkins 批次通知和线上任务详情作为最终证据。
