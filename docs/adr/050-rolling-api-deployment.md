# ADR-050：API 节点滚动发布与纯读 AI 路由容灾

> 注：逐节点滚动顺序已被 ADR-279 的双节点并行发布取代。

## 状态

已采纳。修订 ADR-011 的三节点并行发布策略，并缩小 ADR-034 的 Linux VPN 专用路由范围；
AI 写请求的进一步分流与发布前主动摘流由 ADR-051 补充，节点离线时的成功语义由 ADR-097 更新。

## 背景

`main` 发布会同时在 Linux 主节点和 Windows 从节点重建 `wao-server` 与
`wao-gateway`。云 Nginx 虽然能在单节点失败时切换，但两个上游的重启窗口重合时仍会向页面返回
502/504。

AI 控制台还有第二个放大因素：ADR-034 把整个 `/api/ai/**` 固定到 Linux 主节点。
运行入队、Runner 领取和账号下发确实可能刷新 Codex 令牌，但页面轮询的工作流、执行电脑和
运行列表只读 MySQL，不需要 VPN。它们被一起固定后，主节点重启时无法使用健康的从节点。

## 决策

- CD 按 Windows 从节点→Linux 主节点→云前端/Nginx 的顺序发布。每一段成功后才进入下一段；
  从节点失败时不重启当前健康的主节点，并按 ADR-097 将整体发布判为失败。
- Nginx 对 AI 控制台中明确无外部 AI 请求的 `GET`/`HEAD` 查询使用双 Gateway，并在
  500/502/503/504、连接失败或超时时尝试另一节点。范围包括工作流、执行电脑、运行列表、
  任务运行和项目 AI 配置查询。
- 同路径的非读请求，以及账号管理、Runner 领取/账号下发、页面问答和天人解读，继续固定到
  Linux 主节点，不把需要 VPN 的请求送到 Windows 出口。
- 前端对 `GET`/`HEAD` 收到的 502/503/504 做最多三次短暂退避重试，让单节点或 Nginx 切换期的短暂断连能自动恢复。
  其他状态码不重试，非读请求一律不重放，避免重复写入。
- 线上验收同时检查纯读路由的 `X-WAO-API-Route: dual-gateway-read` 和令牌相关路由的
  `X-WAO-API-Route: linux-vpn-master`，防止以后两类流量被误合并。

## 后果

- 主、从节点都在线时，发布不再同时摘空两个 API 上游；Linux 主节点发布或短暂故障时，AI 控制台的纯读数据可从 Windows 继续读取。
- CD 时间会比三节点完全并行更长，换取的是可用性和清晰的失败边界。
- Windows 从节点离线时，系统只剩一个 API 实例，主节点容器替换期间的短暂不可用无法由本决策消除；
  如需单节点零中断，应另行引入主节点蓝绿容器。
