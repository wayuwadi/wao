# ADR-202：代码交付跟进至合并、上线与验收

## 状态

已接受（2026-09-06）。修订 ADR-199 中允许开发任务以“发布待确认”正常结束的要求，保留一个需求一个 PR、五分钟合批、不可变制品、严格滚动发布和统一协调检查。

## 背景

用户明确要求 WAO 此后改代码必须走完 PR 合并与发布上线。已有流程允许开发任务在本地环境受阻或合并后交还待发布状态，导致交付没有到达用户可用的线上结果。

## 决策

- 代码任务的正常完成条件为：相称测试通过、PR 已合并、成功发布批次包含相关 SHA，并验证线上版本、健康和真实用户操作链路。草稿 PR、合并成功及等待发布均只属于过程状态。
- 沿用现有自动提交、推送、创建 PR、Squash Merge 和发布授权，不逐步重复征求同意。源码仍不得直接推送 main，不放宽凭据保护、已执行迁移或破坏性生产数据操作的限制。
- 优先本地验证真实链路。本地数据库或运行环境连接受阻时完成可执行测试、保留阻塞证据和未验证项，继续已授权的合并发布，在可用真实环境补齐验收；不可把编译、接口成功或页面可达误报为功能验收。
- 多个 PR 仍共用一个批次。现有协调者明确接手后可集中跟进；若没有已确认接手者，当前任务负责到底，不把排队或旧 Skill 的提前结束规则作为默认停止理由。
- 需要异步回访时实际安排同一 Jenkins 任务的唯一回访，保留未完成状态；不能以聊天承诺替代调度。实际失败需定位和处理，确需外部恢复或用户输入时明确报告具体阻塞与剩余动作，不能宣称完成。

## 验证

以正常发布、已有批次排队、本地数据库不可达、发布失败和无明确协调者五种情况检查规则：正常结束均需线上证据，等待期间不重复 Build，真实阻塞不伪报成功。同步项目 AGENTS 与交付技能，旧 ADR 保留为历史决策。本规则修改不改动 Jenkins 调度配置。
