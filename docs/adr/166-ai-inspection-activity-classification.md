# ADR-166：持久化 AI 巡检来源并提供运行结果筛选

## 状态

已采纳。

## 背景

HTTP 性能巡检会创建真实 Task 和 `ai_task_run`，但运行表没有来源分类，首页统一活动查询只能把它当作功能开发。巡检历史又只展示
`automation_run` 的一行结果文案，无法可靠关联后续 AI Run，也没有汇总统计。若前端按任务标题猜类型或只过滤当前页，会造成误分类、
分页总数错误，并让相同运行在多个类型中重复出现。

## 决策

- 为 `ai_task_run` 增加稳定 `activity_type`。普通运行数据库默认及服务端写入均为 `FEATURE_DEVELOPMENT`；HTTP 性能巡检使用专用
  创建入口，在同一事务内改为 `AI_INSPECTION`。
- `JobHandler` 增加向自动化域返回可选 AI Run id 的结构化结果入口。旧执行器由默认实现继续只返回文案；HTTP 巡检同时返回文案和
  新建运行 id，`automation_run.ai_run_id` 持久化关联。
- 统一 AI 活动接口接受类型与结果两个正交筛选。类型支持 `ALL / FEATURE_DEVELOPMENT / AI_INSPECTION / CHAT_REVIEW`，结果支持
  `ALL / SUCCEEDED / FAILED`；筛选发生在计数和分页 SQL 中。
- 巡检历史统计直接由固定自动化任务的真实运行记录计算；单条详情按持久化 `ai_run_id` 按需读取真实 AI Run。未关联记录只展示
  自动化事实，不猜测不存在的 AI 结果。

## 后果

- 巡检运行在首页、完整历史和自动化历史之间具有稳定身份，后续可以继续扩展其它真实巡检类型而无需依赖标题文案。
- V118 对历史的回填严格限定固定巡检任务和标准成功结果；不能证明来源的数据宁可留在原分类。
- 增加一列运行分类和一列可空关联，并为常用筛选建立索引；不修改已执行 migration，也不新增第二份巡检运行数据。
