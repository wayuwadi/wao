# ADR-027：飞书群聊快速收集、验收通知与子任务级 AI 派工

## 状态

已采纳。

## 背景

现在这套东西的入口都在网站上：想法要打开网站新建任务，AI 跑完要打开网站才知道该验收了，
想让同伴一起补充要手动复制链接发到群里。而实际的协作现场在飞书群 —— 想法是在聊天里冒出来的，
稍纵即逝；验收是「有人叫我」才会发生的动作。入口和现场对不上，中间那几步手工操作就是漏斗。

另一边，一个主任务下的子任务粒度差别很大，但派工只能整条任务一起给 AI。子任务想单独跑就得
新建一个任务；而已经跑过的子任务在下一次派工时又会被重新纳入范围，白花算力。

AI 跑完不符合预期时同样只能新建任务重述一遍——已有的续跑只对失败的运行开放。

## 决策

### 1. 群聊是第二个入口

- 新增免登录回调 `POST /api/feishu/events`，填进飞书开放平台的事件订阅。群里 @机器人 说一句话，
  第一行成为任务标题、全文成为描述，落到配置的项目（默认「Wa All in One」），并打上
  「群聊快速收集」标签（`custom` 里的一条属性，事后一眼能认出是随口冒出来的想法）。
- 语音**不做转写**。飞书客户端自带语音转文字，手机上说完直接发文字是最顺的路径；收到语音条时
  回一句提示让对方转文字，而不是接一个转写服务假装能听懂。
- 真实性校验用飞书自己的机制：配了 Verification Token 就校验，配了 Encrypt Key 就按
  AES-256-CBC 解密（密钥是 Encrypt Key 的 SHA-256，密文是 Base64(IV + 密文)）。两者都没配时
  只接受来自已配置群的消息。凭据与其他飞书配置一样加密存 `system_setting`，不进 Git。
- 飞书会重推事件，按 `header.event_id` 在进程内去重，避免一条消息变成两条任务。
- 事件处理里的任何异常都吞掉并记日志，不回 5xx —— 回错误只会让飞书无限重推同一条失败消息。

### 2. 该有人看的时刻，群里说一声

- AI 跑完（无论成功失败）发一张卡片，成功是绿色「去验收任务」，失败是红色「查看失败原因」，
  按钮直接落到那条任务。**通知失败不影响运行结果落库**，只记一条日志。
- 新增任务状态「收集中」。任务一进这个状态就自动分享到群里并 @ 上协作成员 ——
  原来「改状态 → 复制链接 → 发群 → @人」这四步压成一步。只在**进入**该状态时发一次，
  之后再保存任何字段都不会重复打扰群里。
- @ 谁由设置里勾的名单决定，并且永远把操作人自己排掉（自己刚做完的事不用 @ 自己）。
  一个人都不勾就只发通知不 @ 人，对应需求里的「或者是不艾特」。
  操作人的飞书 open_id 通过 `account_identity`（provider=feishu）反查，没绑过飞书就当认不出来。

### 3. 子任务是独立的派工单元

- `ai_task_run` 增加 `sub_id`：为空是整条任务的运行，非空是某一条子任务的运行。两者互不去重，
  主任务在跑不妨碍某条子任务单独跑。
- 子任务运行的提示词地址指向 `/api/share/tasks/{id}/subs/{subId}.md`。
- **主任务派工的提示词地址一律带 `openOnly=true`**，并且 `openOnly` 现在不只过滤已完成的子任务，
  也过滤**已经单独派过工**的子任务。已经有人（有电脑）在做的条目不该再被下一个 AI 当成待办
  重做一遍，这就是需求里的「避免浪费算力」。分享菜单里的开关文案同步改成「只分享还没人做的子任务」。

### 4. 跑完不符合预期时继续，而不是重来

- 续跑（`POST /ai/runs/{runId}/continue`）从「只对失败开放」放宽到「失败和成功都能续」。
  会话 id 和 worktree 都还在原来那台电脑上，所以续跑固定派回它，AI 记得自己改过什么，
  用户只需要说清楚哪 50% 不对。
- Runner 侧的续跑提示词补上交付要求：成功那次已经提交合并过了，不重申一遍「改完还要提交、
  合并、盯部署」，AI 很容易以为本地改好就算完成。

## 后果

- 记录想法的成本从「打开网站新建任务」降到「群里 @ 一下」，代价是多一个免登录回调端点；
  该端点不读写任何用户会话，能做的事只有「在配置好的项目里建一条任务」。
- 「收集中」让状态列从五列变六列。这是有意的：它表达的是「这件事还没定形，欢迎来改」，
  和「待办」是两回事。
- 已经派过工的子任务会从分享清单里消失。如果那次派工失败了、想让主任务重新覆盖它，
  需要先在任务详情里确认；这是刻意选择的保守方向——重复派工的浪费比漏派更贵。
- 通知全部走已有的全局 webhook（ADR-019），快速收集的回执优先用 Open API 回到事件发生的那个群，
  凭据没配好时退回 webhook。
