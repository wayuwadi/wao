# ADR-280：自用系统以发布速度优先的双节点并行发布

- 状态：已采纳
- 日期：2026-09-25
- 取代：ADR-050 的逐节点滚动顺序、ADR-277 的常规发布顺序、ADR-278 的九轮稳定窗口
- 补充：ADR-097、ADR-278 的数据库就绪判定

## 背景

WAO 由维护者本人使用。Jenkins 打包约 1 分钟，发布部署却要 6~8 分钟，且每次发布后云端独立监控都会发出告警与恢复消息。按代码拆解，发布阶段的主要耗时是：

- Linux2 每次强制重建 codex-vpn 与 codex-egress-proxy。两者健康检查间隔 60 秒并串联依赖，首次判定 healthy 就要 2 分钟以上，`wao-server` 必须等它们就绪才启动。
- Linux1 → Linux2 → 云端逐台滚动，每台都要等应用容器 healthy；应用健康检查间隔 15 秒，每级依赖最多多等 15 秒。
- 恢复双节点后固定九轮、间隔 15 秒的稳定窗口（约 2 分钟），以及重复的节点最终验证和 5 次 hello 探测。
- 每次发布都重新部署并验收 JumpServer（三次 Django shell 验证，偶发 SSH 会话失败导致整次发布失败），并重装基础设施清单服务。
- 云端二十余次 SSH/SCP 各自握手；向 Linux1 检查 7 个镜像时逐个经反向隧道往返。

维护者明确选择：发布期间约半分钟的不可用可以接受，目标是部署阶段约 1 分钟，且发布不再产生监控告警。

## 决策

- 常规完整发布同时替换 Linux1 与 Linux2 的应用容器，并同时把云端静态制品预传安装为不可变版本；不再逐台摘流。两台节点都通过节点内验证与云端数据库就绪检查后，才切换公网网页和 Nginx 配置。
- codex 出口代理改用镜像内容标签（`content-<镜像 ID 前 12 位>`），内容不变时 Compose 配置不变，不再重建；内容变化时照常重建。
- 应用容器健康检查间隔从 15 秒改为 3 秒，失败容忍总时长保持不变。
- 去掉九轮稳定窗口、重复的最终节点验证和 hello 探测；公共入口在切换后仍以 `/api/edge/ready` 判定（最多 20 秒收敛），数据库就绪判定口径不变。
- JumpServer 部署与三节点验收只在本批次改到 `deploy/jumpserver/`、无法判定变更范围或重建从库时执行；基础设施清单只在改到 `deploy/infrastructure/` 时重装。
- 云端 SSH 复用单条连接；Linux1 反向隧道会断线重连，不复用。Linux1 已有镜像用一次 SSH 批量判定。已有本地副本的第三方镜像打包时不再访问 Docker Hub。
- 发布开始与结束时 Jenkins 刷新云端 `/run/wao-nginx-upstreams/deploying`。云端独立监控在该标记 10 分钟内不累计任何入口的失败，因此发布不会产生告警，也不会随后发出恢复消息。发布失败由 Jenkins 失败卡片通知；标记过期后持续故障照常告警。
- V77 一次性维护窗口早已完成，并行发布不再实现它；主库状态若不是 `complete`，发布直接失败而不是尝试迁移。

## 后果

- 常规发布期间公共入口会有约 30~40 秒（两台应用 JVM 启动时间）的不可用，前端对读请求的短暂重试仍然有效，写请求可能需要手动重试。
- 节点失败时该节点保持摘流、网页入口保持旧版本，整次发布失败；另一台节点已是新版本，由下次发布或回滚收敛。
- 两台 `wao-server` 同时启动时由 Flyway 的 MySQL 命名锁串行执行 migration。
- 发布结束后 10 分钟内出现的真实故障，要等窗口过期后下一轮监控才告警；以 Jenkins 失败卡片为主要信号。
- 向 Linux1 传输变更的应用镜像仍是完整镜像，是剩余耗时的主要来源；如仍达不到目标，下一步引入按层去重的镜像分发。
