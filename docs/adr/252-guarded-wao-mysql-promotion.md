# ADR-252：WAO 范围的受控 MySQL 接管

## 边界

Linux2 原生 MySQL 还承载 tools、wayuwa、tkwork；其整实例停机或全局只读不是本方案的 WAO 写入隔离手段。Linux1 仍只复制 wao。

接管采用人工批准维护窗口，停止并发发布和特权 WAO 写入，再在 Linux2 对独占 wao 权限的 wao_app 持久 ACCOUNT LOCK，并终止既有连接。锁账户语句关闭当前会话 binlog，不能复制到备用账号。数据库级事件、额外授权和角色先拒绝并要求人工审查。

围栏回执记录源 UUID、已执行 GTID 与时间。Linux1 仅接受两分钟内回执、预期只读角色、同源正常复制、wao.% 过滤和已应用 GTID 屏障。提升停止并移除旧复制通道，但不清空数据或 GTID 历史；通过 SET PERSIST 保存可写角色。命令失败后不能盲目解锁旧主。

该脚本只支持可验证的在线旧主围栏，不把 SSH 超时当成旧主已断电。旧主不可达且没有可核验物理隔离时保持维护状态，不自动提升。root 等特权写入仍须受维护流程约束；这不是硬件围栏或自动故障转移。

## 接管后

两节点应用及 Agent 的 MYSQL_WRITER_HOST 统一改为 10.66.0.3，WAO_MYSQL_PRIMARY=linux1。Linux1 部署校验检查可写角色及不存在旧复制通道；原有副本全量初始化脚本拒绝在该角色下清空卷。主角色必须在共享私有环境中保存，不能只改临时容器。

Linux2 通过命名通道 wao-return 接收 wao.%；旧应用账号一直锁定，另外三个库保持原有写入。过滤同时写入原生 MySQL 启动配置，防止重启丢失动态过滤。禁止自动回切；如需回切必须再建立新的围栏和追平证据。
原生 MySQL 主配置和返回通道配置一并进入已有加密恢复包，不把配置中的私有内容写入仓库。

四库备份继续在 Linux2 采集三个写主库与 WAO 副本，但每轮全量和 binlog 归档必须验证新主 UUID、通道状态、延迟，并等待新主当前 GTID 屏障应用。log_replica_updates 必须开启，所以新主的 WAO 事务进入 Linux2 的连续归档日志。不再称 Linux2 为四库写主；来源拓扑写入快照元数据。

Linux2 或反向复制失联时不能继续声明四库恢复点新鲜，归档拒绝并由独立节点告警。仅剩一台机器时无法继续产生异机副本，这是现有两数据节点的能力边界。

## 验证

实际备用账号已补齐，应用通过私网登录成功，写入被只读错误 1290 拒绝。隔离双 MySQL 9.7 使用生产核心函数测试围栏、GTID 屏障、提升、反向复制和备份来源校验；临时数据、网络和容器在结束时清理。生产切换另需维护窗口批准，不以隔离测试冒充生产接管完成。

依据：[MySQL 9.7 动态复制过滤不持久](https://dev.mysql.com/doc/refman/9.7/en/change-replication-filter.html)、[按通道配置启动过滤](https://dev.mysql.com/doc/refman/9.7/en/replication-rules-channel-based-filters.html)。
