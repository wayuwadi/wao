# ADR-311：每个发布批次自动更新 Git 记录

- 日期：2026-10-03
- 状态：已接受（用户明确要求任何 Git 提交与发布都更新记录）

## 问题

页面代码多次发布，但人工 `currentRelease.json` 未修改，顶栏和最近更新仍显示上次介绍。只补文案或提醒维护无法满足自动更新要求。

## 决定

1. 当前版本说明与 Git 档案由构建时的完整 HEAD 自动生成，记录该 HEAD 可达的全部提交（含文档、测试、合并），不读取提交正文、作者邮箱或未合并分支。构建缺少历史、版本不一致时失败，不静默复用旧说明。
2. 同一份数据绑定页面常量、既有版本检测清单和不可变 `git-history.json`。旧页面从自己的制品路径读取，拒绝不同 SHA；仍通过原保存屏障更新，不强制刷新或覆盖草稿。
3. 自动记录与人工精选并存。精选缺失不阻止新版本说明更新；已有精选归档检查保留。UI 显示提交时间，不伪造发布时间；前端版本包含提交不等于其他服务全部部署。
4. 调整原变更范围策略：每个 main 批次至少构建并发布网页静态制品。文档、测试或其他不改变运行行为的提交不重建后端镜像、不重启后端。一次批次包含多个提交时全部收录，不要求每条提交单独发布。
5. 既有一分钟批处理、唯一协调者和游戏独立制品机制继续使用；主站为更新记录始终构建，游戏仍按实际改动范围构建。旧桌面客户端与 Runner 不重新启用。
6. Jenkins 的 Node slim 容器没有 Git，由宿主完整可信 checkout 导出只含 SHA、提交时间及标题的输入，容器核对首条 SHA。普通本地构建直接读 Git，不依赖额外 API/账号。

## 边界与代价

每个 main 批次增加主站静态构建成本，换取更新记录随版本自动维护。原“纯文档无需任何部署”的表述改为“后端无需部署，网页更新记录需要刷新”。已经合并但尚未完成发布的提交不会提前出现在旧制品中；失败发布不切换记录，回退沿用旧制品记录。

Jenkins 当前不可用，规则以本地 Git/脚本测试验证；本次实际发布使用已有 Windows 临时通道，不声称 Jenkins 已实际运行。其他工作区未来仍须通过现有协调流程发布，不能把本次改动称作新增自动发布服务。
