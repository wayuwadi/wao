# ADR-278：发布成功以数据库就绪和稳定窗口为准

> 注：九轮稳定窗口已被 ADR-280 取消；数据库就绪判定口径保留。

- 状态：已采纳
- 日期：2026-09-24
- 补充：ADR-277、ADR-253

## 故障证据

Jenkins #517 于 23:12:40 发送发布成功通知，但 23:13 起用户请求出现 10 秒超时，云端三个入口随后连续就绪失败。Linux2 应用日志从 23:13:36 起反复记录 MySQL 连接已关闭；稍后出现新连接握手读超时、Hikari 获取连接 30 秒超时和 JDBC 会话读取失败。Linux2 的 `wao-mysql-primary-tunnel.service` 在 23:32:57 再次启动，调查时累计重启五次；MySQL 服务自身运行超过 32 天，没有在此次故障中重启。现有发布验证仅检查容器 `healthy`、`/api/hello` 和一次数据库只读状态查询；`/api/hello` 无法证明应用经 SSH 通道连接写库。

## 决策

- 节点本地、云端到两节点、公共入口的发布验证统一使用 `/api/edge/ready`，同时检查 HTTP 成功、响应 `code=0` 与 `data.protocol=1`。该路由由应用查询当前写库的只读状态，通道失效时不能误报成功。
- 最终两节点探测和节点验证显式检查退出码并写失败状态；发布脚本仅启用 `set -u`，不能依赖 shell 自动在命令失败时停止。
- 完整发布恢复双节点回流后，持续进行九轮检查，轮间隔 15 秒，覆盖至少两分钟的延迟故障窗口。任何一轮失败即标记发布验证失败，不发成功通知；原有云端独立监控继续告警，不因本次改动静默。
- 滚动发布期间的公共入口可用性监视也改用数据库就绪路由，避免 `/api/hello` 掩盖数据层中断。纯网页快路径仍做前后单轮验证，不额外等待稳定窗口。

## 边界与后续决策

此变更修正“已经不可用却报告发布成功”的验收错误，不能修复 Linux2 到 Linux1 写库的物理网络或 SSH 通道本身。现行写主位于 Linux1，两节点和云端都依赖其可达性；再次发生公网链路故障时仍会有真实中断。要消除这类单点，需要另行评估写主位置、传输冗余和数据恢复演练，按 `docs/runbooks/mysql-guarded-recovery.md` 审核后实施；不能通过放宽就绪条件或禁用告警掩盖它。
