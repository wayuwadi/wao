# 可逆交付与验证

## 改动前

- 确认授权范围、当前分支/环境和工作区已有改动的归属。
- 阅读与接口、数据、部署或体验相关的规格和 ADR。
- 定义失败收口；涉及数据删除、覆盖、生产写入或外部消息时先解析精确目标。
- 接口、数据结构或部署行为变化时同步文档；已执行 migration 只能新增，不能修改。

## 实现中

- 先修根因，再处理同范围的低代价完整性问题。
- 固定流程优先写成确定性代码或脚本；模型负责需要语义判断的部分。
- 对外部操作使用幂等键、条件更新或可重试协议，避免超时后重复副作用。
- 保留加载、失败、空状态和恢复路径；后台轮询不能覆盖本地草稿。

## 验收

按风险从内到外验证：

1. 针对核心逻辑的测试或静态检查。
2. 受影响模块的构建与回归。
3. 真实用户操作链路，包括失败和恢复。
4. 合并后的部署终态、线上结果与通知回执由发布协调者统一检查，不占用每个开发线程。

记录实际执行的命令、关键结果和未执行项的原因。失败日志保留相关步骤和完整根因，不用“应该没问题”代替证据。

## 交付

提交和 PR 描述解释改动、原因与验收。开发交付须确认本地真实用户链路通过、目标分支包含变更；发布尚未确认时明确写“本地已验收，发布待确认”，不称已上线。按 ADR-199 和 wao-dev-batch-delivery Skill 将同一 Jenkins 任务的发布检查集中给一个协调者，以历史成功部署耗时安排检查；其他开发线程不阻塞等待，不重复轮询。只有有部署终态与线上证据时才称“已上线”；发布异常与本地开发结果分别报告。
