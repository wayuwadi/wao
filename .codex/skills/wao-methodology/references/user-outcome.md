# 用户结果与需求判断

## 从现象到目标

依次写清：

1. 用户现在看见或经历了什么。
2. 用户建议了哪种解决手段。
3. 用户真正想获得的结果是什么。
4. 哪些现有行为不能被破坏。

用户描述通常是现象，不预设根因。先读实现和数据流；多条抱怨可能来自同一病灶，一条抱怨也可能由多处代码叠加。

## 真实链路检查

- 数据从哪里产生、谁有权读取、何时更新、失败时显示什么？
- 页面状态是否覆盖加载、空数据、编辑草稿、保存中、已保存、失败重试？
- 多人或定时刷新会不会覆盖本地未保存输入？
- 弹窗、窄屏、长标题、大量页签和慢网络下是否仍能完成操作？
- 成功通知之外，失败是否给出原因和可执行的恢复入口？

没有真实数据源、官方接口或可靠实现条件时，删除或不实现伪功能，并说明边界。不要用硬编码、随机数或静态示例伪装真实业务能力。

## 方案比较

只比较会改变结果的选项。每个选项写明：用户收益、实现与运维成本、权限和数据风险、可逆性、验收方式。

优先选择能产生完整真实闭环的最小方案。局部代码更少但要求用户长期人工补洞，不算更简单。
